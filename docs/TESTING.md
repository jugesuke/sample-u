# 実機確認の手順

ハードウェアを含めた動作確認の手順と、問題が出たときの情報の集め方をまとめます。ログの形式は[仕様書 7章](SPEC.md#7-ログ)を参照してください。

小さい構成から順に確認します。問題が出たら、その段階で止めて原因を調べてから先に進みます。

## 0. 準備

1. Webアプリを公開先に反映します。GitHub Actionsの成功を確認してください。
2. スマホのChromeで公開URLを開きます。更新が反映されないときは、再読み込みします。
3. ファームウェアをArduino IDEで書き込みます。手順は[README](../README.md#ファームウェアの書き込み)を参照してください。

アプリとファームウェアは、指令フレームの形式が一致している必要があります。片方だけ古いと船は動きません(ログに `bad` が増えます)。

## 1. XIAO単体

XIAOを基板から外し、USBで給電します。モーターを動かさずに、BLEとログを確認します。

書き込み直後は起動理由が `POWERON` にならないことがあるので、USBを一度抜き差ししてから始めます。ログ画面の表示レベルは `DEBUG` にします。

| 確認内容 | 合格の目安 |
|---|---|
| 「船に接続」で `SampleU-Boat` が出て接続できる | `接続完了` が出る |
| 起動ログが届く | `boot reason=POWERON` |
| 指令が届く | `tx` と `rx` の `seq` がほぼ揃って増え、`lost=0`、`bad=0` |
| 無操作時の受信 | 1秒ごとの `rx` 行で `n` が約20、`gap` が100ms未満 |
| 前進の操作 | `rx` の `L`、`R`、`out` が追従し、全開で `duty=1023/0,1023/0` |
| 後進の操作 | 全開で `duty=0/1023,0/1023` |
| 画面を消して、再び表示する | 約0.5秒で止まったことを示す `failsafe stop: no command` が残っている |

ここで動かなければ、回路ではなくソフトウェアかBLEの問題です。

## 2. 基板に搭載

USBを外してからXIAOを基板に載せます。プロペラは付けず、モーターは固定します。

1. **電源投入時の動き:** 接続しないまま電源を5回ほど入れ直し、モーターが一瞬でも回らないか確認します。D9のプルアップにより、左モーターが回る可能性があります([仕様書 10章](SPEC.md#10-回路上の注意))。
2. **起動:** 接続して `boot reason=POWERON` を確認します。`BROWNOUT` なら、起動時点で電圧が足りていません。
3. **低出力の回転:** 「最大」を30%にして、「左右独立」モードで左右を1つずつ動かします。
4. **回転方向:** 前進の操作で、各モーターが前進方向に回るか確認します。逆に回るときは、スケッチ冒頭の `MOTOR_L_INVERT` / `MOTOR_R_INVERT` を `true` にして書き込み直します。

## 3. 停止と負荷

プロペラは付けずに確認します。

| 確認内容 | 合格の目安 |
|---|---|
| 操作中に「切断」を押す | 0.5秒以内に止まる |
| 操作中に画面を消す | 0.5秒以内に止まる |
| 操作中にスマホのBluetoothを切る | 0.5秒以内に止まる |
| STOP | 解除するまで動かない |
| 最大100%で急に前後を反転する | `boot reason=BROWNOUT` が出ない、切断しない |
| 全開を1分ほど続ける | ドライバICが異常に熱くならない |
| 消耗した電池(2V台前半)で動かす | 動作が安定し、ドライバICが異常に熱くならない |

単3電池2本では、モーターの始動電流による電圧低下でXIAOが再起動する可能性があります。`BROWNOUT` と切断を重点的に確認してください。

消耗した電池での確認は、IN入力がVCCを超える条件の確認も兼ねています([仕様書 10章](SPEC.md#10-回路上の注意))。

## 4. 水上

1. **防水と回収:** 水が入らないことと、止まったときの回収手段を先に確認します。最初は浅い水槽か、紐を付けた状態で行います。
2. **水中の負荷:** プロペラを付けて、3の負荷の確認を繰り返します。空転より負荷が大きくなります。
3. **通信距離:** 少しずつ離して、`gap` と `lost` が増え始める距離と、`failsafe stop` が出る距離を記録します。使用する場所より広い距離まで確認します。

## モーターが回らないときの電圧測定

スマホを操作せずに測るときは、確認用スケッチ `firmware/motor_test/` を書き込みます。電源を入れて約2秒後から、左前進、左後進、右前進、右後進を10秒ずつ、間に2秒の停止を挟んで繰り返します。確認後は `firmware/boat_controller/` を書き込み直します。

GND基準で次を測ります。右は `U4` で同じ箇所を測ります。

| 測定箇所 | 前進 | 後進 |
|---|---|---|
| 1番 IN_A | 約3.3V | 約0V |
| 3番 IN_B | 約0V | 約3.3V |
| 4番 VCC | 電池電圧 | 電池電圧 |
| 7番 OUT_A | 約VCC | 約0V |
| 5番 OUT_B | 約0V | 約VCC |

## 問題が出たときの情報の集め方

### 集める情報

1. ログ画面の「保存」で出力したファイル。表示レベルに関係なく全行が入ります。
2. 確認の段階と、行った操作。
3. 実際の動き(例: 左だけ回らない、1秒後に止まる)。
4. 発生した日時。ログの日時はUTCなので、日本時間から9時間引いた時刻で探します。
5. 電池の状態(新品か使用済みか、測れれば電圧)。
6. 再現するかどうかと、その頻度。
7. ファームウェアの `build=` の値(`boot` の行にあります)。

アプリのログは最新10000行までです。古い行から消えるので、問題が起きたら早めに保存します。「クリア」を押してから再現させると、関係する行を探しやすくなります。

船のログは起動後の未送信分だけが船のRAMに残ります。電源を切ると消えるので、**問題が起きたら電源を切る前にアプリで接続し直してください**。

### ログの見方

表示レベルを `INFO` にして異常の有無を見てから、`DEBUG` にして指令の流れを追います。

| ログの状態 | 判断 |
|---|---|
| `a`、`b` が操作に反応しない | 操作部の問題 |
| `a`、`b` は動くが `L`、`R` が変わらない | `max`、`bal`、`stop` を確認 |
| `tx` が出ない、`seq` が増えない、`skip`、`fail` が多い | 送信の問題 |
| `tx` の `seq` は増えるが、`rx` が追いつかない、`n=0`、`lost` が多い | 無線区間の問題 |
| `bad` が増える | アプリとファームウェアの形式の不一致 |
| `rx` の `L`、`R` は正しいが `out` が追従しない | 船の制御の問題(`failsafe stop` を確認) |
| `duty` は出ているがモーターが回らない | 配線、ドライバIC、モーター、電池など回路側の問題 |
| `boot reason=BROWNOUT` | 電圧低下による再起動 |
| `boot reason=PANIC`、`*_WDT` | ファームウェアの異常による再起動 |

`rx` 行が届かないときは、指令は届いていてログの通知だけが止まっている可能性もあります。モーターの実際の動きと合わせて判断します。

ログで確認できるのは `duty` までです。モーターの回転、電流、電池電圧は記録されないので、必要ならテスターなどで測定します。
